
# Documentación del Proyecto Agribar

## 1. Resumen del Proyecto

**Agribar** es una aplicación de escritorio desarrollada en Flutter, diseñada para la gestión integral de nóminas en el sector agrícola. El sistema permite administrar empleados, cuadrillas, actividades y procesar la nómina semanal, culminando con la generación de reportes de gastos.

La aplicación se conecta directamente a una base de datos PostgreSQL para todas sus operaciones, funcionando como un cliente pesado. Está estructurada para soportar múltiples roles de usuario con diferentes niveles de acceso y permisos.

## 2. Tecnologías Principales

- **Framework Frontend:** Flutter 3.x
- **Lenguaje de Programación:** Dart
- **Base de Datos:** PostgreSQL
- **Plataformas Soportadas:** La estructura del proyecto está preparada para macOS, Windows y Linux.
- **Dependencias Clave:**
  - `postgres`: Para la conexión directa con la base de datos PostgreSQL.
  - `fl_chart`: Para la generación de gráficas en el dashboard.
  - `window_manager`: Para controlar el tamaño y comportamiento de la ventana en escritorio.
  - `excel`, `pdf`: Para la exportación de datos y reportes.

## 3. Arquitectura y Flujo de Datos

Agribar sigue una arquitectura de cliente pesado. La aplicación Flutter contiene toda la lógica de negocio y se conecta directamente a la base de datos PostgreSQL, sin una capa de API o backend intermedia.

El flujo general es el siguiente:
1.  **Autenticación:** El usuario inicia sesión con sus credenciales. El `ControlUsuarioService` las valida contra la tabla `usuarios` en la BD.
2.  **Permisos:** Según el rol del usuario (`Administrador`, `Supervisor`, `Capturista`), la aplicación habilita o deshabilita el acceso a las diferentes secciones (Nómina, Empleados, Configuración, etc.).
3.  **Operación:** El usuario interactúa con las diferentes pantallas (módulos). Cada acción (ej. crear un empleado, registrar una actividad, cerrar una semana) ejecuta consultas SQL directamente sobre la base de datos a través de los `services`.
4.  **Visualización:** Los datos obtenidos de la base de datos se renderizan en la interfaz de usuario a través de los `widgets` y `screens`.

## 4. Módulos Principales

El sistema se divide en los siguientes módulos funcionales, accesibles desde el `DashboardScreen`:

### 4.1. Autenticación (`Login_screen.dart`)
- **Propósito:** Validar el acceso de los usuarios.
- **Servicios Involucrados:** `ControlUsuarioService`, `UsuariosService`.
- **Lógica:** Compara el nombre de usuario y la contraseña (actualmente sin encriptar) con los registros en la tabla `usuarios`. Si es exitoso, carga los permisos del rol asociado y navega al `DashboardScreen`.

### 4.2. Dashboard (`modern_dashboard.dart`)
- **Propósito:** Ofrecer una vista general y en tiempo real del estado del sistema.
- **Funcionalidades:**
  - Muestra métricas clave: total de empleados, cuadrillas, gasto de la semana.
  - Presenta gráficas sobre la distribución de gastos por cuadrilla.
  - Muestra rankings (Top 3) de cuadrillas, ranchos y actividades con mayores gastos.
- **Lógica:** Realiza múltiples consultas `SELECT` con agregaciones (`SUM`, `COUNT`, `GROUP BY`) sobre las tablas `nomina_empleados_semanal`, `cuadrillas`, `ranchos` y `actividades` para obtener los datos.

### 4.3. Empleados (`Empleados_content.dart`)
- **Propósito:** Gestión del personal. Permite crear, ver, editar y habilitar/deshabilitar empleados.
- **Servicios Involucrados:** `cargarEmpleadosDesdeBD.dart`, `registro_empleado_service.dart`.
- **Lógica:** Interactúa principalmente con la tabla `empleados`.

### 4.4. Cuadrillas (`Cuadrilla_Content.dart`)
- **Propósito:** Administrar los equipos de trabajo.
- **Servicios Involucrados:** `cargarCuadrillasDesdeBD.dart`.
- **Lógica:** Gestiona los registros de la tabla `cuadrillas`.

### 4.5. Actividades (`Actividades_content.dart`)
- **Propósito:** Definir las labores que se pueden asignar y su costo.
- **Servicios Involucrados:** `registrar_actividad.dart`.
- **Lógica:** Administra la tabla `actividades`, donde cada actividad tiene una clave, nombre e importe.

### 4.6. Nómina (`Nomina_screen.dart`)
Este es el módulo más complejo y central del sistema.
- **Propósito:** Orquestar todo el proceso de pago semanal.
- **Flujo de trabajo:**
  1.  **Crear/Seleccionar Semana:** El usuario crea una nueva semana de trabajo (`SemanaService`).
  2.  **Armar Cuadrillas:** Se asignan empleados a las diferentes cuadrillas para esa semana.
  3.  **Captura de Datos:** Para cada empleado, se registran los pagos diarios y las actividades/campos asociados a cada día.
  4.  **Cálculos:** El sistema calcula totales, subtotales y neto a pagar.
  5.  **Guardado:** Los datos se guardan en la tabla `nomina_empleados_semanal`.
  6.  **Cierre de Semana:** Una vez finalizada, la semana se "cierra", lo que probablemente mueve los datos a una tabla de historial (`nomina_empleados_historial`) y bloquea la edición.
- **Servicios Involucrados:** `SemanaService`, `CuadrillasCache`, `database_service.dart`.

### 4.7. Reportes (`Reportes_screen.dart`)
- **Propósito:** Generar informes de gastos basados en los datos históricos.
- **Servicios Involucrados:** `reportes_service.dart`.
- **Lógica:** Realiza consultas complejas sobre la tabla `nomina_empleados_historial` para agregar datos por rancho, actividad y rangos de fechas.

## 5. Estructura de la Base de Datos (Inferida)

Basado en los servicios, se puede inferir el siguiente esquema de tablas principal:

- `usuarios`: Almacena las credenciales y el rol de cada usuario.
  - `id_usuario`, `nombre_usuario`, `correo`, `contraseña`, `rol` (FK a `roles`).
- `roles`: Define los perfiles de usuario y sus permisos.
  - `id_rol`, `descripcion`, `acceso_nomina`, `acceso_configurar_usuarios`, etc.
- `empleados`: Catálogo de trabajadores.
  - `id_empleado`, `codigo`, `nombre`, `apellido_paterno`, `habilitado`, etc.
- `cuadrillas`: Catálogo de equipos de trabajo.
  - `id_cuadrilla`, `clave`, `nombre`, `estado`.
- `actividades`: Catálogo de labores y sus costos.
  - `id_actividad`, `clave`, `nombre`, `importe`.
- `ranchos`: Catálogo de campos o lugares de trabajo.
  - `id_rancho`, `nombre`.
- `semanas_nomina`: Define los periodos de nómina.
  - `id_semana`, `fecha_inicio`, `fecha_fin`, `esta_cerrada`.
- `nomina_empleados_semanal`: Tabla transaccional principal donde se captura la nómina activa.
  - `id_nomina`, `id_semana`, `id_cuadrilla`, `id_empleado`, `dia_1` a `dia_7`, `act_1` a `act_7`, `campo_1` a `campo_7`, `total`, `total_neto`, etc.
- `nomina_empleados_historial`: Probablemente una tabla para almacenar los datos de las semanas ya cerradas para la reportería.

## 6. Estructura del Proyecto

- `lib/main.dart`: Punto de entrada de la aplicación. Inicializa Flutter y la configuración de la ventana.
- `lib/screens/`: Contiene los widgets que representan cada pantalla/módulo principal.
- `lib/services/`: Contiene la lógica de negocio y las clases que interactúan directamente con la base de datos. Es el "backend" de la aplicación.
- `lib/widgets/`: Widgets reutilizables más pequeños (botones, tablas, diálogos) que se usan en las pantallas.
- `lib/theme/`: Define los estilos visuales de la aplicación (colores, fuentes, temas).
- `pubspec.yaml`: Define las dependencias del proyecto y la configuración general.
- **Scripts en la raíz (`debug_*.dart`, `corregir_*.dart`)**: Una colección de scripts de Dart para ejecutar tareas de mantenimiento, depuración y consulta directamente sobre la base de datos. **Nota:** Es una práctica inusual tenerlos en la raíz de un proyecto Flutter. Normalmente, estas herramientas se desarrollarían como una aplicación de consola separada o se integrarían en una sección de administración dentro de la propia app.

## 7. Observaciones y Puntos de Mejora

- **Falta de Pruebas Automatizadas:** El proyecto carece de un directorio `test`, lo que indica una ausencia total de pruebas unitarias, de widgets o de integración. Esto es un riesgo significativo para la mantenibilidad y la introducción de nuevos cambios.
- **Lógica de Negocio en el Cliente:** Toda la lógica, incluidas las credenciales de la base de datos, reside en el cliente. Esto puede ser un riesgo de seguridad si la aplicación se distribuye ampliamente. Para un entorno controlado (ej. una sola oficina), puede ser aceptable.
- **Ausencia de un Backend:** La conexión directa a la base de datos acopla fuertemente el frontend a la estructura de la BD. Un cambio en el esquema puede requerir una actualización completa de la aplicación cliente. Una API REST o gRPC podría desacoplar esto.
- **Manejo de Contraseñas:** Las contraseñas se manejan en texto plano (`_hashPassword` simplemente retorna la contraseña). Es **crítico** implementar un sistema de hashing (como `bcrypt` o `argon2`) para almacenar las contraseñas de forma segura.
- **Scripts en la Raíz:** Los numerosos scripts de Dart en la carpeta raíz deberían organizarse mejor, quizás en una carpeta `tools` o `scripts`, y documentar su propósito y uso.
- **Gestión de Estado:** El estado parece manejarse principalmente con `StatefulWidget` y `setState`. Para una aplicación de esta complejidad, considerar un gestor de estado más robusto (como Provider, BLoC, o Riverpod) podría simplificar el código y mejorar el rendimiento.
- **Migraciones de BD:** El archivo `database_migration_service.dart` sugiere un intento de manejar cambios en el esquema de la BD. Este es un buen inicio, pero debería formalizarse en un sistema de migración más robusto y versionado.
